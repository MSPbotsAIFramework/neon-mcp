## Product design

### Goals / Non-goals

**Goals**: a first version of `neon-mcp` that lets an agent, acting on behalf of one Neon account (identified by the caller's own Neon API key, forwarded per request), inspect and manage that account's Neon **infrastructure** through Neon's public REST API:

- See what projects exist in the account.
- See, create, and delete branches inside a project — branching (instant copy-on-write of a database) is Neon's own core differentiator and the most likely reason an agent would want "live access" to Neon rather than just a static connection string.
- See the compute endpoints (the running Postgres instances) attached to a project.
- See, and create, databases and roles inside a branch.
- Get a ready-to-use connection string (URI) for a given project/branch/database/role.
- Check whether an asynchronous change (branch create/delete, database/role create) has finished, so the agent knows when it is safe to use the thing it just created.

**Non-goals** (v1):

- **Running SQL against the data a Neon branch holds.** Neon's REST API is a control plane for the *infrastructure* (projects/branches/computes/databases/roles); it has no endpoint that executes a query. Reading or writing actual table rows would require a native Postgres wire-protocol connection using the connection string this MCP can hand back — a completely different client, a completely different security posture (arbitrary SQL execution through the gateway on behalf of a tenant), and a different kind of review. Out of scope for this ticket; if ever wanted, it is a separate ticket with its own threat model, not an extension of this one.
- Organization-level management, billing/consumption history, VPC endpoints, project-level API key management, Neon Auth, serverless Functions, and "Realtime" subscriptions. These categories were reported by an automated summary of Neon's docs index page but **were not independently confirmed against endpoint paths** during this design pass (see Tech design → Decisions made by DEV01, item 3); excluding them is the safe default, not a shortcut.
- Updating or suspending compute endpoints, renaming projects/branches, deleting databases/roles/projects, and rotating role passwords. Bounding the write surface to "create a branch for testing" + "create a database/role in it" keeps the blast radius of a mis-called tool small; the rest is a follow-up if a concrete need shows up.
- Any UI. This is a backend MCP connector with no end-user-facing screen; "space with empty/loading/error states" does not apply.

### Acceptance criteria AC1..AC15

- **AC1**: Given a valid Neon API key header, When the caller asks what Neon projects exist, Then the connector returns the project list (id, name, region, created_at) with no other input required.
- **AC2**: Given a project, When the caller asks for its branches, Then the connector returns each branch's id, name, parent branch id, default/protected flags, and current state.
- **AC3**: Given a project (and optionally a source/parent branch), When the caller asks to create a new branch, Then the connector creates it and returns the new branch's id plus the operation(s) tracking the creation.
- **AC4**: Given a project and a branch, When the caller asks to delete it without explicitly confirming, Then the connector does **not** call Neon's delete endpoint and instead tells the caller confirmation is required.
- **AC5**: Given a project and a branch, When the caller asks to delete it **with** explicit confirmation, Then the connector calls Neon's delete endpoint and returns the operation(s) tracking the deletion.
- **AC6**: Given a project, When the caller asks what compute endpoints exist, Then the connector returns each endpoint's id, branch id, type (read-write/read-only), and current state.
- **AC7**: Given a project and a branch, When the caller asks for its databases, Then the connector returns each database's name and owning role.
- **AC8**: Given a project and a branch, When the caller asks to create a new database with a name and an owner role, Then the connector creates it and returns the created record.
- **AC9**: Given a project and a branch, When the caller asks for its roles, Then the connector returns each role's name and whether it is a system-protected role.
- **AC10**: Given a project and a branch, When the caller asks to create a new role, Then the connector creates it and returns its name; if Neon returns a generated password with the creation response, the connector surfaces it once to the caller in that same response and never stores or logs it.
- **AC11**: Given a project, branch, database, and role that all exist, When the caller asks for a connection string, Then the connector returns the full Neon connection URI for that combination.
- **AC12**: Given a project, When the caller asks whether a recent operation (from AC3/AC5/AC8/AC10) has finished, Then the connector returns that operation's current status.
- **AC13**: Given no Neon API key header on the request, When any tool is called, Then the connector returns a structured 401 naming the required header, and no call reaches Neon's API.
- **AC14**: Given an invalid or revoked Neon API key, When any tool is called, Then the connector surfaces Neon's 401/403 as a structured error (code + message), not a raw stack trace or an unhandled 5xx.
- **AC15 (multi-tenant isolation)**: Given two different Neon API keys used in two concurrent requests (two different Neon accounts), When each request is handled, Then each one only ever sees/affects the Neon account tied to its own header — the server holds no cross-request cache or shared state that could leak one account's data into another's response.

## Tech design

### Conclusion

Build `neon-mcp` from scratch (main line A) against Neon's public REST API (`https://console.neon.tech/api/v2`, Bearer-token auth, no login/paywall — confirmed in the prior `[BLOCKED]` comment and re-confirmed in this pass via `https://neon.com/docs/reference/api-reference`). Follow the `hudu-mcp` repo shape (same org, same stack, newest fully-built reference per `[[project_prd21298_box_empty_scaffold_repo]]`'s note that `dropbox-mcp` was also just a scaffold) for module layout, credential middleware, structured error envelope, and response-size capping; adapt for Neon's single fixed host (no per-tenant base-URL header needed, unlike Hudu which is self-hosted) and cursor-based pagination.

### Where the current implementation lives

Nowhere yet — `neon-mcp@main` (2ee9ed0) is a two-line README with no source tree. There is no prior Neon connector in `MSPbotsAIFramework` to extend (confirmed by org-wide search in the earlier `[BLOCKED]` comment on this ticket).

### Option analysis

- **Build from Neon's REST API directly (chosen)**: public, free, Bearer-token auth, documented resource model (projects → branches → endpoints/databases/roles), matches every other first-party connector in this org (HTTP wrapper over a vendor REST API, credentials from a request header). No sign-up gate, no partner/paid tier blocking any of the resources this design uses — unlike Dubber/IQMS, nothing here needed a `[BLOCKED]`.
- **Wrap Neon's official MCP server** (Neon publishes its own open-source MCP, referenced from their docs) — rejected per the vendor-mcp-development SOP: "open source / third-party MCP repos are reference only, always reimplement from scratch in `MSPbotsAIFramework`, never fork/mirror/directly modify". Used only as a sanity check on tool naming/resource shape, not as code.
- **Proxy the Postgres wire protocol (let the agent run SQL)** — rejected, see Non-goals: different protocol, different risk profile, not what a REST-API-shaped connector in this org does.

### Data & API contract

**Transport**: Streamable HTTP, stateless, one container serving every tenant (SOP's three rules: credentials from headers only, per-request isolation, no server-side state).

**Credential header**:

| Header | Required | Meaning | How to get it |
|---|---|---|---|
| `X-Neon-API-Key` | Yes | Neon personal or organization API key, forwarded as `Authorization: Bearer <key>` to `console.neon.tech` | Neon Console → Account settings → API keys (self-service, no partner/paid gate) |

No base-URL header: Neon's API has exactly one host, unlike self-hosted vendors (Hudu) — same reasoning as the Figma design (`[[project_prd21325_figma_new_mcp_build]]`).

**Upstream base URL**: `https://console.neon.tech/api/v2` (confirmed via `https://neon.com/docs/reference/api-reference`).

**Tool → endpoint map**:

| Tool | Method & path | Notes |
|---|---|---|
| `neon_list_projects` | `GET /projects` | params: `limit`, `cursor`, `search` passthrough |
| `neon_get_project` | `GET /projects/{project_id}` | |
| `neon_list_branches` | `GET /projects/{project_id}/branches` | params: `limit`, `cursor` |
| `neon_get_branch` | `GET /projects/{project_id}/branches/{branch_id}` | |
| `neon_create_branch` | `POST /projects/{project_id}/branches` | body: optional `branch_name`, optional `parent_id` |
| `neon_delete_branch` | `DELETE /projects/{project_id}/branches/{branch_id}` | requires `confirm: true` argument (AC4/AC5); without it, the tool returns an error and never calls Neon |
| `neon_list_endpoints` | `GET /projects/{project_id}/endpoints` | |
| `neon_get_endpoint` | `GET /projects/{project_id}/endpoints/{endpoint_id}` | |
| `neon_list_databases` | `GET /projects/{project_id}/branches/{branch_id}/databases` | |
| `neon_create_database` | `POST /projects/{project_id}/branches/{branch_id}/databases` | body: `database_name`, `owner_name` |
| `neon_list_roles` | `GET /projects/{project_id}/branches/{branch_id}/roles` | |
| `neon_create_role` | `POST /projects/{project_id}/branches/{branch_id}/roles` | body: `role_name`; response may include a one-time generated password — passed through, never stored/logged |
| `neon_get_connection_uri` | `GET /projects/{project_id}/connection_uri` | params: `database_name`, `role_name`, `branch_id`, optional `pooled` |
| `neon_list_operations` | `GET /projects/{project_id}/operations` | params: `limit`, `cursor` |
| `neon_get_operation` | `GET /projects/{project_id}/operations/{operation_id}` | used to poll AC3/AC5/AC8/AC10 until `status` is a terminal value |

**Pagination**: Neon list endpoints are cursor-based (`cursor` query param + `limit`, default 10 / max 400 per the OpenAPI spec fetched in this pass). List tools pass `cursor`/`limit` straight through and return whatever next-cursor field Neon's response includes; `_json.dump_json_capped`'s own pagination-safe truncation (reused from `hudu-mcp`) still applies as a second, response-size-driven safety net.

**Errors**: the exact error-body schema did not resolve in this pass (Neon's docs reference a `$ref: GeneralError` that this pass's doc fetch did not expand). Design follows `hudu-mcp`'s defensive pattern rather than assume a schema: classify by HTTP status first (`_STATUS_TO_CODE`: 400/409/422 → `invalid_argument`, 401/403 → `unauthorized`, 404 → `not_found`, 429 → `rate_limited` retryable, 5xx/0 → `upstream_error` retryable), then best-effort extract a human message from the body (`error`/`message` keys if present, else the raw status line) — same approach as `hudu_mcp._error_message`, which does not depend on knowing the exact field names in advance and degrades gracefully if Neon's error shape differs per endpoint.

**Logging**: one line per upstream call — `method`, `path`, `status`, `ms`, `attempt` (no request/response bodies, no API key) — same as `hudu-mcp`'s `logger.info(...)` call. This satisfies the ticket's "every action logged" with the same meaning used by every other connector in this org (see Open question Q1).

### Key flow / sequence

Typical "spin up a test branch and hand back a connection string" flow:

1. Agent calls `neon_list_projects` (or already has a `project_id`).
2. Agent calls `neon_create_branch(project_id, branch_name="pr-1234-test")` → Neon returns the new branch plus one or more `operations` (branch creation is asynchronous).
3. Agent polls `neon_get_operation(project_id, operation_id)` until `status` is terminal (e.g. `finished`).
4. Agent calls `neon_create_database(project_id, branch_id, database_name, owner_name)` (optional — Neon may auto-create a default database with the branch; the tool is available for when a specific name/owner is needed) and/or `neon_create_role`.
5. Agent calls `neon_get_connection_uri(project_id, branch_id, database_name, role_name)` → gets back a ready-to-use Postgres connection string for whatever client needs to connect over the wire protocol (outside this MCP's scope — see Non-goals).
6. When done, agent calls `neon_delete_branch(project_id, branch_id, confirm=true)` to tear the test branch down.

### Non-functional

- **Idempotency/concurrency**: every tool call builds its own `NeonCredentials`/`NeonClient` from the current request's header via a `contextvars.ContextVar` set by the middleware and reset in `finally` (copied from `hudu-mcp`); the shared `httpx.AsyncClient` connection pool never holds credentials, so concurrent calls from different tenants cannot see each other's key. Writes (`create_branch`/`create_database`/`create_role`/`delete_branch`) are not retried on ambiguous failures (status `0` or `>=500`) — only GETs are retried, same rule as `hudu-mcp`, so a write is never silently run twice.
- **Performance**: no SLA stated in the ticket; inherits the org-wide per-call budget (`_CALL_BUDGET_SECONDS = 100`, gateway tool-call timeout 120s) and the existing retry/backoff shape. List tools are capped by Neon's own `limit`/`cursor` pagination plus the response-size safety net in `_json.py`.
- **Security**: credential read only from `X-Neon-API-Key`, never persisted to disk/env/logs (SOP §3.1); 401 on missing header before any upstream call (SOP §3.2); `neon_get_connection_uri`'s response contains a role's password inside the URI — documented in the tool's description as sensitive, and the server-wide logging policy (method/path/status only, no bodies) already keeps it out of logs. `neon_delete_branch` requires `confirm: true` (AC4/AC5) as the one destructive tool in v1.
- **Multi-tenant isolation**: AC15; same guarantee hudu-mcp documents (per-request context var, no module-level credential state, cookie jar rejects all cookies so no session leaks across tenants sharing the process).
- **Observability**: one structured log line per upstream call (method/path/status/ms/attempt), no secrets — see Data & API contract → Logging.

### Rollout & rollback

Brand-new connector, no existing tenants/consumers to break. Dev leg develops on `dev/PRD-21329` off the latest `main`, runs the repo's own tests plus a local `initialize → tools/list` smoke test with placeholder headers, then (per `mcp-track.md` §3) hands off to the review leg, which merges to `main`, registers the vendor on INT (`mcppub register`, since this is a brand-new vendor not yet known to the deploy API), and publishes. **Release order: no dependency** — single repo, nothing else to sequence against (no `mixed` platform half, no other MCP this one depends on).

Rollback: revert the merge commit on `main` and re-publish (or unregister the vendor) if INT health checks or registration fail; no data migration, no schema, nothing to roll back on Neon's side (this connector creates no persistent state on Neon or in MSPbots beyond what the agent/tenant explicitly asks for via `neon_create_*` tools).

- **Regression surface**: none yet — new repo, nothing to regress.

### Effort & breakdown

Story points: 3

Tier 3 ("new subsystem, bounded"), same tier as the Box/Plaid/Figma precedents in this batch, not tier 5:

- New repo, new vendor API (unknown-but-now-researched external surface) — pushes above 1–2.
- Bounded, well-documented REST API, single fixed host, single credential header, no OAuth/multi-tier credential model (unlike Plaid's app+per-customer token split) — keeps it from tier 5.

- No UI, no migration, no cross-repo coordination (`release order: none`) — none of the tier-5 drivers (multi-repo dependency chains, data migration, breaking changes to an existing tenant-facing contract) apply.

- **No Neon test account configured in this pipeline's environment**: not a blocker per SOP; dev leg runs everything mockable, flags account-dependent cases `untested`/`blocked` with the reason, same precedent as Box/Plaid/Figma.
- **Dependency**: none on another ticket. Single repo, `release order: none`.

## Decisions made by DEV01

(Also posted as a separate `[DESIGN DECISIONS]` ClickUp comment per `mcp-track.md` §2.4.)

1. **Scope is Neon's management/control-plane REST API only, not SQL execution against the data it holds.** Why: those are two different protocols (HTTP REST vs. the Postgres wire protocol) with very different security postures (infrastructure management vs. arbitrary query execution through the gateway on behalf of a tenant); every other connector in this org is a REST wrapper, not a data-plane client. Alternative not chosen: building a tool that opens the returned connection string and runs arbitrary SQL — rejected as a materially different, higher-risk capability that deserves its own ticket and its own review.
2. **Single credential header `X-Neon-API-Key`, no base-URL header.** Why: Neon has exactly one fixed API host (`console.neon.tech`), unlike self-hosted vendors (Hudu) that need a per-tenant base URL. Alternative not chosen: accepting Neon's own `Authorization: Bearer` header directly from the caller — rejected per the SOP's header-naming convention (`X-<Vendor>-<Credential>`), which keeps the gateway's own auth header free of vendor credentials.
3. **"Additional Categories" (Organizations, Snapshots, Functions, Realtime, Neon Auth, VPC endpoints, consumption history, project-level API keys) excluded from v1.** Why: these were reported by an automated doc-index summary, not independently confirmed against Neon's OpenAPI spec within this pass. Alternative not chosen: including them on the summary's word alone — rejected as the kind of unverified claim this SOP explicitly warns against (`docs-tree.md` §7: "a description of current state is not evidence either").
4. **`neon_delete_branch` requires an explicit `confirm: true` argument; no other delete tools in v1.** Why: branch deletion is destructive and irreversible from the MCP's point of view (it does not undo a Neon operation); the `hudu-mcp` precedent uses the same `confirm: true` gate for its delete tools. Alternative not chosen: deleting on the first call — rejected as too easy to trigger accidentally from an agent's own planning mistake.
5. **Write surface bounded to branch create/delete + database/role create.** Why: covers the "spin up and tear down a test branch" workflow the ticket's "live access" framing most plausibly wants, without adding endpoint suspend/resume, project/branch rename, or database/role/project deletion, each of which is a separate, reversible-scope decision better made against a concrete need. Alternative not chosen: mirroring every CRUD endpoint Neon exposes — rejected as unbounded scope for a first version with no specific requirement driving it.
6. **Error handling classifies by HTTP status first, parses `error`/`message` best-effort second**, same pattern as `hudu-mcp`. Why: Neon's generic error schema (`$ref: GeneralError`) did not resolve to concrete fields during this design pass; status-code classification does not depend on knowing the exact body shape and degrades gracefully. Alternative not chosen: hand-writing a Neon-specific error parser against an assumed schema — rejected as likely to break silently against Neon's real responses.
